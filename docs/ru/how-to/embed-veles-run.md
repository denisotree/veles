# Как встроить `veles run` в другую программу

> 🌐 **Языки:** [English](../../en/how-to/embed-veles-run.md) · **Русский**

`veles run` — поддерживаемый способ вызывать Veles из другой системы: конвейера
мониторинга, шага CI, cron-скрипта. Это обычный подпроцесс: на вход промпт, ответ в
stdout, диагностика в stderr, итог в коде выхода. Ни демона, ни HTTP, ни WebSocket.

Предпочитайте его [демону](run-as-daemon.md), если не нужны постоянная сессия или
каналы. `POST /v1/runs` возвращает id запуска, а не ответ — текст получает только
подписчик WebSocket, так что вызывающей стороне без интерфейса читать нечего.

## Вызов

```python
subprocess.run(
    ["veles", "run", "--verbose", prompt],
    cwd=project_dir,
    capture_output=True, text=True,
    stdin=subprocess.DEVNULL,
    timeout=600,
)
```

В этом фрагменте четыре вещи несут нагрузку.

**Флаги — после глагола.** `veles run --verbose "…"`, но не
`veles --verbose run "…"`. Разбираются оба варианта, но учитывается только первый —
см. [Позиция флагов](#позиция-флагов) ниже.

**`stdin=subprocess.DEVNULL` обязателен.** Проверки разрешений отказывают
автоматически, когда нет TTY, а эта проверка смотрит только на `sys.stdin`. Родитель,
который перехватывает stdout и stderr, но оставляет stdin подключённым к терминалу,
доходит до интерактивного меню и висит до вашего таймаута.

**Ставьте `timeout` сами.** Своего ограничения по времени у Veles нет. Внутренние
потолки — `--max-tokens-total` (по умолчанию 100 000) и `--max-iterations` (по
умолчанию 1000; это страховка от зацикливания, а не бюджет задачи).

**`cwd` решает, куда попадут относительные пути.** `--project-root` перенаправляет
собственное разрешение путей Veles (память, поиск инструментов, артефакты), но не
рабочий каталог, поэтому свой инструмент с `open("out.json", "w")` всё равно пишет
относительно `cwd`.

## Контракт вывода

| Поток | Содержимое |
|---|---|
| stdout | текст итогового ответа и один завершающий перевод строки. Больше ничего. |
| stderr | `<session=…>`, `<finished after …>`, `error: …`, `warning: …`, прогресс |

Оба утверждения проверяет `tests/test_cli_run_contract.py`, так что это контракт, а не
наблюдение.

`--verbose` добавляет пошаговый журнал прогресса и итоговую строку, в которой видны
причина остановки и расход токенов:

```
<finished after 7 turns, reason=completed, budget=8412/100000>
```

Два флага лежат **вне** этого контракта:

- `--stream` отправляет в stdout прозу каждого раунда, включая пояснения перед вызовом
  инструмента, — не только итоговый ответ. Не используйте его, если разбираете stdout.
- `--manager` возвращается раньше строки сессии и сопоставления кодов выхода.

Для медленной модели `--stream` не нужен. Без него Veles всё равно получает ответ потоком
от любого провайдера, который это умеет, и печатает только итоговый ответ. Поэтому
таймаут запроса (`[engine] request_timeout_s`) ограничивает паузу между чанками, а не
весь ответ: медленная локальная модель работает, пока пишет, а зависший сервер
по-прежнему ловится.

### Вызовы инструментов в `events.jsonl`

Чтобы посчитать или проверить вызовы инструментов, читайте
`<project>/.veles/events.jsonl` — по JSON-объекту на строку. Каждый вызов — строка
`tool_call`, его результат — строка `tool_result` с тем же `tool_call_id`:

```json
{"type": "tool_call", "ts": "…", "session_id": "…", "tool_call_id": "c1", "name": "btgate_query", "arguments": {"…": "…"}}
{"type": "tool_result", "ts": "…", "session_id": "…", "tool_call_id": "c1", "name": "btgate_query", "output": "…", "error": null}
```

Эти ключи входят в контракт (`tests/test_cli_run_contract.py`); могут появиться новые,
так что незнакомые пропускайте. Строка `tool name(args)`, которую `--verbose` печатает
в stderr, — отладочный вывод, а не часть контракта; не разбирайте её.

Это верно для API-провайдеров (`openrouter`, `openai`, `anthropic`, `gemini`,
локальных). С CLI-делегатом (`claude-cli`, `codex`, `antigravity-cli`) делегированный
CLI вызывает инструменты Veles через собственный MCP-сервер, и эти вызовы в
`events.jsonl` не пишутся.

## Коды выхода

| Код | Значение | Что делать вызывающему |
|---|---|---|
| 0 | completed | использовать ответ |
| 1 | ошибка провайдера или нераспознанное незавершение | повторить |
| 2 | не настроена модель, нет API-ключа, неизвестный id для `--resume`, нет проекта | исправить настройку; не повторять |
| 3 | `max_iterations` | сузить задачу или поднять `--max-iterations` |
| 4 | `budget_exhausted` | поднять `--max-tokens-total` |
| 5 | `empty` — модель не выдала итогового текста | повторить |
| 6 | `cancelled` | прервано |

Причина остановки, добавленная в более поздней версии, отображается в 1, так что
неизвестный исход никогда не примут за успех.

## Свои инструменты

Инструмент — функция с декоратором `@tool()` в `<project>/.veles/tools/*.py`; аннотации
типов становятся его JSON-схемой. На двух проверках люди спотыкаются.

**`veles trust set <tool>` ничего не делает для обычного своего инструмента.**
Лестница доверия срабатывает только для инструментов с `sensitive=True`. У простого
`@tool()` нет класса риска, он разрешается в `allow` и никогда не проверяется —
разрешение записывается, но не читается.

**Настоящая проверка — `veles tool approve`**, и она привязана к хешу файла. Скрипт
развёртывания одобряет ровно то содержимое, которое просмотрел человек:

```bash
veles tool approve                            # список неодобренных файлов с их sha256
veles tool approve my_tool --sha256 <hash>    # TTY не нужен; падает, если файл изменился
```

Закрепите проверенный хеш в своём развёртывании. Если файл с тех пор изменился, команда
падает, а не одобряет новое содержимое. `--yes` пропускает вопрос только в терминале
(с 1.2.8): без терминала `run_shell` агента мог бы одобрить им собственные инструменты.

**Любая правка сбрасывает одобрение.** Неодобренный файл пропускается — модель не видит
ни инструмента, ни отказа, поэтому агент может уверенно ответить, так и не добравшись
до своего источника данных. С v0.30 пропуск печатает в stderr
`warning: N self-authored tool file(s) not loaded (unapproved): …`; следите за этой
строкой и одобряйте заново после каждой записи. Файл, который импортируется, но не
определяет ни одной функции с `@tool` (например, argparse-скрипт агента), — тоже не
инструмент: `veles tool approve` предупреждает `… defines no @tool function — nothing will
be registered` (и всё равно завершается с кодом 0 — одобрены байты), а каждый запуск
печатает в stderr `warning: tool file <name>.py not loaded: …`, как и для файла, который
не удалось импортировать.

**С модулями так же.** Код модуля выполняется на каждом ходе агента, поэтому модуль
загружается, только пока его файлы совпадают с одобренным хешем:

```bash
veles module show my_guard                       # манифест и sha256 файлов
veles module approve my_guard --sha256 <hash>    # TTY не нужен; падает, если файлы изменились
```

`veles doctor` сообщает об ошибке для каждого модуля на диске, который не загружается, —
запускайте его в стартовой проверке. Административные глаголы (`module`, `tool`,
`doctor`, …) никогда не открывают мастер первого запуска, даже на чистом `$HOME` с TTY;
он стоит только перед командами, запускающими агента, и там его пропускает
`VELES_NO_WIZARD=1`.

**В Docker песочница `run_shell` по умолчанию выключена.** С 1.2.9 shell-команды агента
выполняются в песочнице ОС, где git-хуки, состояние Veles и хранилища одобрений для них
только для чтения; в непривилегированном контейнере `bwrap` не может создать свои
пространства имён, поэтому `run_shell` работает без песочницы, а `veles doctor`
предупреждает. Либо запускайте контейнер с
`--security-opt seccomp=unconfined --security-opt apparmor=unconfined` (это ослабляет
собственный профиль контейнера), либо монтируйте `~/.veles/*approvals*.json` и
`~/.veles/extensions.json` только для чтения, чтобы хранилища одобрений были вне
досягаемости агента.

Ещё два острых угла:

- `@tool(timeout_s=…)` носит рекомендательный характер — его никто не соблюдает.
  Ограничивайте медленную работу внутри инструмента (таймаутом запроса на стороне
  клиента), а не декоратором.
- Возвращённая `str` длиннее `max_result_chars` (по умолчанию 8000) выгружается в
  `.veles/artifacts/` и заменяется превью. Агрегируйте на стороне сервера.

### Структурированный результат без разбора прозы

Аргументы вызова инструмента уже проверяются по схеме, так что второй инструмент —
самый дешёвый машиночитаемый канал, поддержка ядра не нужна:

```python
@tool()
def emit_result(status: str, detail: str) -> str:
    """Record the final structured result. Call exactly once, last."""
    out = Path(".veles/tmp/result.json")
    out.parent.mkdir(parents=True, exist_ok=True)
    out.write_text(json.dumps({"status": status, "detail": detail}))
    return "recorded"
```

Читайте файл после завершения процесса; если его нет, берите прозу из stdout, а не
теряйте результат. Удаляйте файл перед каждым запуском, чтобы не прочитать устаревший.

### Ограничение набора инструментов

Отдельного файла набора инструментов на проект пока нет, а в `[permissions]` нет
`deny` — допустимые значения: `allow`, `approval_required` и `always_confirm`. Раз
запуск без TTY отказывает автоматически, для вызывающей стороны без интерфейса
`always_confirm` фактически означает запрет:

```toml
# <project>/.veles/config.toml
[permissions]
fetch_url  = "always_confirm"
web_search = "always_confirm"
```

## Память между вызовами

Каждый запуск — отдельная сессия, и всё безусловно пишется в `memory.db`. Разница
лишь в том, найдёт ли это *следующий* запуск.

**Промпт — это запрос к памяти, дословно.** Короткие запросы объединяются через AND —
хорошо для поиска по ключевому слову. Длинные объединяются через OR и ранжируются по
релевантности: требование, чтобы одна сохранённая строка содержала *каждый* токен
абзаца, ничего не находит, как только в нём есть метки времени, id и значения метрик.
До v0.31 длинные запросы тоже шли через AND и молча не находили ничего.

Ранжированное пересечение всё равно слабее точного запроса, поэтому держите промпт
коротким и стабильным, а объёмные данные передавайте файлом:

```python
(project_dir / ".veles/tmp/input.json").write_text(json.dumps(payload))
prompt = f"Investigate {stable_topic_key}. Input: .veles/tmp/input.json"
```

**Записывайте важное детерминированно.** Автоматический извлекатель инсайтов
срабатывает только на явные сигналы («запомни…», «никогда…») или на ошибку
инструмента, поэтому обычный запуск чаще всего ничего долговременного не пишет.
Вставьте строку сами — подойдёт обычный SQLite, а FTS-триггеры её проиндексируют:

```python
with sqlite3.connect(project_dir / ".veles/memory.db") as c:
    c.execute(
        "INSERT INTO insights(title, body, category, created_at, confidence) "
        "VALUES (?,?,?,?,?)",
        (title, body, f"topic/{stable_topic_key}", time.time(), 1.0),
    )
```

**И читайте обратно тоже детерминированно.** `memory_query` — SQL только для чтения
поверх `memory.db`, и он есть в наборе инструментов по умолчанию. Велите агенту начать
с него — и извлечение больше не зависит от удачи ранжирования:

```sql
SELECT title, body, created_at FROM insights
WHERE category = 'topic/<key>' OR category = 'curated-session'
ORDER BY created_at DESC LIMIT 10
```

Обратите внимание на второе условие: куратор складывает свои выжимки под
`curated-session`, а не под ваш ключ.

Полезно знать:

- **`rules` обходят ранжирование полностью.** Дайджест правил попадает в стабильную
  часть системного промпта, в отличие от найденных инсайтов, которые соревнуются за
  пять мест. Долговременным рабочим фактам место там (`memory_save_rule`); дайджест
  вмещает 12 правил, так что расходуйте их обдуманно.
- **Вывод инструментов не индексируется.** Поиск по ходам охватывает только сообщения
  пользователя и ассистента. Свидетельство, которое должно сохраниться, должно попасть
  в инсайт или в текст ответа.
- **`.veles/memory/insights/*.md` — отрисованное представление, по нему не ищут.**
  Класть туда markdown бесполезно.
- Recall отбрасывает инсайты с уверенностью ниже 0.3.
- API обновления или удаления инсайтов нет. Чтобы списать инсайт, замените его через
  `insight_refs` — recall такие отфильтровывает.

### Флаги, меняющие то, что накапливается

- **`--resume` отключает обучение.** Он пропускает куратора и извлекатель инсайтов и
  повторно использует системный промпт, зафиксированный при старте сессии, — ни свежего
  recall, ни свежего дайджеста правил. Используйте новую сессию на каждый вызов, а
  непрерывность пусть несёт память.
- **`--no-insights`** выключает извлечение инсайтов. Оставьте его включённым.
- **`--no-curator`** заодно отключает послеходовый dream, предложения навыков и
  предлагатели. Его единственный плюс — задержка: куратор — синхронный проход LLM,
  который откладывает завершение процесса. Если ставите его, запускайте `veles curate`
  по расписанию.
- **`veles dream --include-consolidation`** — флаг важен. Дедупликация инсайтов и
  дозаполнение эмбеддингов идут только под ним, так что простой `veles dream` оставляет
  дубликаты несхлопнутыми, а векторы — незаписанными.

Семантическому recall инсайтов дополнительно нужен **локальный** бэкенд эмбеддингов
(Ollama с `nomic-embed-text`); облачный API-ключ его не включает, и это намеренно —
текст проекта никогда не уходит облачному эмбеддеру. Без локального бэкенда recall
остаётся только по ключевым словам. Какой бэкенд активен, показывает `veles doctor`.

## Параллельность

На проект один `memory.db`, поэтому запуски против одного проекта сериализуйте на
стороне вызывающего. Разные проекты (`--project-root`) независимы.

## Позиция флагов

`veles` принимает общие флаги цикла агента и до глагола, и после него, потому что
голый `veles` запускает REPL и нуждается в них на верхнем уровне. До v0.30 флаг,
поставленный *перед* глаголом, молча отбрасывался: `veles --verbose run "x"` терял
`--verbose`, а `veles --provider anthropic run "x"` работал на openrouter, подавляя
настроенный в проекте провайдер. Теперь обе позиции равнозначны, но если вы закреплены
на старой версии, ставьте флаги после глагола.
